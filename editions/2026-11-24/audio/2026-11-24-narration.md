# Ruby's string bug is critical, so check your version before lunch

*The spoken edition of The Working Copy for 2026-11-24. Narrated by Uncle Burt.*

Here's the thing about this week: Ruby, the language, had a memory bug in the part of itself that changes the case of strings. Lowercase to uppercase, that thing. The boringest operation in computing. And it turned out to be a critical flaw that default Rails and Sinatra apps reach before anyone even logs in. If you have ever wondered whether security work is fair, here is your answer: the attack surface includes the alphabet. Let's explain the bug in plain words, because the phrase heap buffer overflow gets thrown around like everyone knows what it means. A program gets handed a chunk of memory with an edge to it. A buffer overflow means the program writes past that edge, into whatever was sitting next door. It's like writing on a sticky note and just keeping going, onto the desk, the laptop, and eventually the operating system's diary. Corrupt the right neighbor and you can steer the program in whatever direction you like. The sticky note never signed up for that. So what happened here, specifically, is that Ruby's string case-conversion code could be pushed past the end of its memory. The Ruby team disclosed it on November nineteenth and rated it critical, and they say proofs of concept exist that achieve remote code execution, which is the polite phrase that means an attacker can run their own code on your machine. The trigger is casing a string. You do not need a login. You do not need a clever payload. The door is the doormat. The reach is what makes this one genuinely rude. Veria Labs found that Ruby on Rails applications, and classic-style Sinatra applications, hit this bug in their default configuration. Default. Not a weird plugin you installed at two in the morning, not an exotic setting you enabled because a forum post from twenty thirteen told you to. The configuration that exists the moment you finish the tutorial is the configuration that is exposed. And the exposure happens before authentication, which means the login screen that makes you feel safe is standing behind the hole, not in front of it. That's an important bit of set design to picture correctly. There is good news, and it is the good news you actually want: fixes exist on every maintained release line. The patched versions are Ruby three point three point fourteen, three point four point thirteen, and four point oh point ten. Whichever line you're on, there is a patched release waiting on it. You do not need a major-version jump. You do not need a migration saga with a support group. You need to be on one of those versions, and then you can go back to whatever you were pretending to work on. But before you upgrade anything, you need to know what you actually run, and this is where everyone, myself very much included, embarrasses themselves during a security scare. You upgrade the Ruby you think you run instead of the Ruby you actually run. And Ruby versions live in several places at once, like a bad housemate. There's the version pinned in your repository's toolchain files. There's the version your terminal resolves to right now. And there's the version your Rails and Bundler gems were installed against. Three answers to one question, and they do not always agree. Sometimes they disagree loudly. The gap between those versions is exactly where memory bugs hide, because your app doesn't run the version in your head. It runs the version something resolves at deploy time, and that something has opinions you forgot you gave it. So the first move in this whole story is not an upgrade. It's an audit. Find out what's actually running, and be prepared to be mildly insulted by the answer. I have never once done this check and felt proud afterward. It's always a little archaeology. You dig, and you find a version from a previous era of your life, sitting there like it belongs. This is where the example on the page earns its keep. There's a block you can run against your own repository, and it prints the Ruby, Rails, and Bundler versions your app actually resolves, plus the local toolchain versions. The output is a short table. If the Ruby line shows three point three point fourteen, three point four point thirteen, four point oh point ten, or anything later, you're patched. Congratulations. Return to your day with a smugness you have genuinely earned, and it will be gone by lunch, but enjoy it. If the Ruby line shows anything older than those, you have found your afternoon. And I want to be clear about the script itself: it changes nothing. It only reports. It's a diagnostic, not a surgeon. You can run it anywhere without fear, which is the correct temperament for a first step in a security incident. Look before you patch. Measure before you cut. Panic last, and only recreationally. Now, a wrinkle, and it's a big one if you run self-hosted software. A pile of products that bundle their own Ruby shipped an affected version in their latest release at the time of disclosure. That list includes GitLab, GitHub Enterprise Server, Mastodon, OpenProject, Discourse, and Chatwoot. If you run any of those, the bug is inside a product, not inside your own code, which means the upgrade path goes through their release feeds, not your Gemfile. Watch for their patched builds. You can't fix their bundle from your side, and honestly, they wouldn't want you to try. Meanwhile, there's a safety net, and unusually for this industry, it's free. Cloudflare's web application firewall, which is just a filter sitting in front of your app blocking known attack patterns, now blocks this bug for every customer, including Free plans. Two new rules went into both the Free Managed Ruleset and the Managed Ruleset, on by default, set to Block. One covers this flaw, and the other covers a related integer overflow in the same string case-conversion code that was fixed in the same releases. One upgrade closes both doors, which is efficient, in the way that only consequences can be. And here's the part I genuinely like: Cloudflare's own post is blunt about the limits. The firewall is a compensating control, not a replacement for patching, because exploits can reach the bug through paths a firewall cannot see. It's the vendor saying, in public, that their net has holes in it. Refreshing honesty, mildly alarming implication. The firewall is the seatbelt you wear while the airbag gets installed. You want both. You only truly need the airbag. But wear the seatbelt anyway, because the airbag is on a truck somewhere and the road is right now. Let's be careful about what the source actually establishes versus what it can't. The source shows the flaw exists, that it's rated critical, that fixes shipped in those three releases, that Rails and Sinatra hit it by default per Veria Labs, and that the firewall rules exist and block by default. What it cannot establish is your specific exposure. Whether your app is exploitable depends on your versions, your traffic, and your setup, and no blog post on earth knows that. Only the version check on your machine does. The internet is very confident and very general; your terminal is quiet and specific. Trust the quiet one. So the order of operations, one more time, slowly. Run the version check against your repository. Note the Ruby line. If it's one of the patched versions or later, you're done, and honestly, well done. If it's older, plan the upgrade now, before the proofs of concept grow up into working exploit kits, because they always do. That is not cynicism; that is the lifecycle. Your next concrete step is simply running the check. It changes nothing, it takes a minute, and it replaces a vague ambient dread with a specific, fixable fact. That's the best trade in software. Here's a detail worth savoring: the Cloudflare rule that catches part of this pattern wasn't even built for Ruby. The post mentions that an earlier update for related PHP flaws had already been blocking a slice of this attack class before anyone disclosed the Ruby bug. Which means the firewall was partially prepared for a problem it hadn't been told about, through no virtue of its own, just overlapping signatures. That's how a lot of security luck actually works. Nobody planned it. The patterns just happened to rhyme. It also explains why the blocking rules shipped so quickly: half the plumbing was already in the wall, waiting for someone to notice the alphabet was load-bearing. Go make it.
