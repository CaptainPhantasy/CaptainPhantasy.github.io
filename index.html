You do not train the GGUF, you train the model behind it

You cannot fine-tune a GGUF file. Every published walkthrough starts with the model's original weights, trains a small adapter against them, merges it back, and only then converts the result into the packed file that Ollama runs. The order is the lesson.

The GGUF is the finishing move

A GGUF is not a training format. It is the packed file that llama.cpp and Ollama run. In both of the published walkthroughs this edition draws on, the GGUF appears at the end: you train a model, merge the adapter, convert the merged model, quantize it, and only then serve it.

What gets trained is a low-rank adapter, usually called LoRA. Instead of rewriting every weight in the base model, you train a small set of extra weights that sit beside the frozen model and steer its behavior. QLoRA is the same idea with one more economy: the frozen base model is loaded in a compressed four-bit form, which is what lets a modest graphics card hold a model that would not otherwise fit. You train the adapter against that compressed model, then merge it into a full-precision copy later.

Start with a small base model. The beginner guide uses Phi-3-mini, a model under four billion parameters that loads in four-bit form in about six gigabytes of graphics memory, which is small enough for a free cloud notebook. The same guide puts seven- and eight-billion-parameter models at roughly twelve gigabytes, and a nine-billion model at about fourteen. The pipeline does not change with size; the small model just fails faster and costs less to fix.

Your data decides whether it works

Fine-tuning is not a way to pour facts into a model. The beginner guide lists fine-tuning to add facts as a common mistake and points to retrieval instead: search your own documents, hand the useful passages to the model, and let it answer from them. What fine-tuning is good at is behavior: the shape of an answer, a house style, a strict output format, a consistent way of classifying a request.

The file is usually JSON Lines: one example per line, each one a short conversation with a system instruction, a user message and an assistant reply. The twelve-step walkthrough uses prompt and completion objects instead, and notes that the training loss is computed only on the completion, meaning the assistant's answer is the part being taught. Either format works. What matters is that every line is valid, every example has an assistant turn, and the assistant turn is last.

Hold examples back. The twelve-step walkthrough starts with eight hundred training rows and one hundred test rows, and those hundred never enter training; they are how you find out whether the model learned the task or memorized the answers. The beginner guide's advice on size is several hundred to a few thousand well-curated examples. Before any of it, run the check on the page: it reports malformed lines, missing assistant turns and the shortest and longest example. It cannot judge quality, but it makes the cheap failures loud.

Train, merge, convert, run

The twelve-step walkthrough's settings are a reasonable default: rank sixteen, alpha thirty-two, a small dropout, all linear layers, a learning rate of two times ten to the minus four, two epochs and an eight-bit paged optimizer. It warns against raising the learning rate for luck; push it higher and the loss can turn into not-a-number.

When training finishes, merge the adapter into a full-precision copy of the base model, on the processor, and never into the compressed four-bit weights. The walkthrough is explicit: merging into the compressed weights re-quantizes the model and discards much of what the adapter learned. Then convert the merged model to a full-precision GGUF and quantize it, commonly to a four-bit format. On the walkthrough's larger example the practical disk requirement is a hundred and fifty gigabytes, and the full-precision file is the first thing to delete after the quantized one passes.

The last piece is the Modelfile, the recipe Ollama uses to create a runnable model. The walkthrough starts from the base model's own Modelfile, which already contains the right chat template and stop tokens, and changes only the line that names the source file. The chat template is the format the model expects for a conversation: where the system prompt goes, how the user's turn is marked, how the assistant's turn begins. The beginner guide calls a template mismatch one of the hardest problems to diagnose, and the walkthrough warns that missing end-of-sequence handling causes endless generation. Evaluate on the held-out rows with temperature at zero, and count a parse failure as a miss.

Why it matters

  • Both walkthroughs end at GGUF, so the file you download is the last thing you make, not the first thing you train.
  • A model under four billion parameters can train on a free cloud GPU, which makes the whole pipeline reachable from a laptop.
  • The chat template and the end-of-sequence token are the difference between a working model and one that babbles forever.

Copy snippet

#!/usr/bin/env python3
"""Check a JSONL chat file before you spend GPU hours training. Read-only."""
import json
import pathlib
import sys


def messages_of(row):
    if not isinstance(row, dict):
        return None
    if isinstance(row.get("messages"), list):
        return row["messages"]
    if isinstance(row.get("prompt"), list):
        return row["prompt"] + (row.get("completion") or [])
    return None


def problem(line):
    try:
        row = json.loads(line)
    except ValueError as exc:
        return f"not valid JSON ({exc.msg})"
    messages = messages_of(row)
    if not messages:
        return "no messages list"
    for message in messages:
        if not isinstance(message, dict) or not isinstance(message.get("content"), str) or not message["content"].strip():
            return "a message has no text content"
    roles = [message.get("role") for message in messages]
    if "assistant" not in roles:
        return "no assistant turn"
    if roles[-1] != "assistant":
        return "last message is not the assistant"
    return ""


def main():
    if len(sys.argv) != 2:
        raise SystemExit("usage: check-dataset.py train.jsonl")
    path = pathlib.Path(sys.argv[1])
    lines = [(number, line) for number, line in enumerate(path.read_text(errors="replace").splitlines(), 1) if line.strip()]
    problems, sizes = [], []
    for number, line in lines:
        issue = problem(line)
        if issue:
            problems.append(f"line {number}: {issue}")
        else:
            sizes.append(sum(len(message["content"].split()) for message in messages_of(json.loads(line))))
    print(f"examples: {len(lines) - len(problems)} of {len(lines)} non-empty lines")
    if sizes:
        print(f"words per example: {min(sizes)} to {max(sizes)}")
    print(f"problems: {len(problems)}")
    for item in problems:
        print(item)


if __name__ == "__main__":
    main()
