# ruby2shell can corrupt memory in a default Rails app before login

*The spoken edition of The Working Copy for 2026-11-27. Narrated by Uncle Burt.*

Here's the thing about this episode: the bug lives in the part of Ruby whose entire job is being nice about strings. Not some obscure corner of the standard library nobody visits, not a protocol parser you opted into after reading a consent form. Changing the case of text. Upcasing, downcasing, the stuff you do without thinking, the stuff the language is famous for making pleasant. On November nineteenth, the Ruby team disclosed a heap buffer overflow hiding in exactly that code, rated Critical, with proofs of concept that already achieve remote code execution in some scenarios. Let's be precise about what a heap buffer overflow actually is, because the term gets thrown around like everyone was born knowing it. A program gets handed a chunk of memory, and it writes past the end of that chunk. The trouble is what happens next. The overflow lands on adjacent memory, corrupts it, and in the worst case the machine ends up executing instructions the attacker chose. That's why the words Critical and remote code execution get to sit in the same sentence, and why the Ruby team saying it's aware of working proofs of concept should take this out of the theoretical column entirely. The fixes shipped in Ruby three point three point fourteen, three point four point thirteen, and four point oh point ten. Hold onto those three numbers. Now the part that makes this worse than your average Wednesday disclosure. Security researchers at Veria Labs found that Ruby on Rails applications and classic-style Sinatra applications hit this bug in their default configuration, before any authentication. Not after a login. Not behind some feature you forgot you enabled back in twenty twenty-one. Before anyone proves they're anyone. The front door of a default app is already standing open to this thing. If you're running a hobby project you assumed was too small to matter, congratulations, you're in the exact demographic this bug had in mind. And the reach keeps going. Self-hosted products that bundle their own Ruby shipped an affected version in their latest release at the time of disclosure. The list includes GitLab, Mastodon, Discourse, OpenProject, Chatwoot, and GitHub Enterprise Server. The supply chain doesn't care whose name is on the manifest. There's also a second flaw, an integer overflow in the same string case conversion code, tracked as its own advisory and fixed in the same three releases. Two bugs, one root cause, one upgrade that closes both. Cloudflare got involved too, and to their credit, in the way that actually matters: their Web Application Firewall now blocks this for every customer, including people on the Free plan. Not a paid tier quietly enjoying safety while the free tier gets a shrug and a support forum. The rules were added to both of their managed rulesets, with Block as the default action, covering both this bug and the related integer overflow. But Cloudflare themselves say it plainly, and I want to underline it in the voice of someone who has watched a stopgap quietly become permanent architecture: the firewall is a compensating control, not a replacement for patching. Exploits can reach the bug through paths a filter never sees. It's a seatbelt. And anyone who has ever said "we'll fix it after the launch" knows exactly how seatbelt-shaped decisions age. Which brings us to the actual skill this episode wants to teach, and it's a small one that pays for itself every single time something like this lands. The trap in Ruby version management is the gap between the Ruby you think you're on and the Ruby your application actually resolves. Your repository pins a version in its configuration files. Your terminal has whatever your version manager last installed, which is whatever you needed for a different project three weeks ago. Production has whatever the container image baked in months ago, back when that felt like a responsible choice, and to be fair, it was one at the time. Those are three different numbers all wearing the same name badge, and every one of them will swear under oath that it's the real one. At least two of them are lying, and one of them is your production server. The runnable example in this edition exists to collapse that confusion into a single report. It reads the Ruby, Rails, and Bundler versions your repository resolves from its own configuration files, and then reports the versions from your local toolchain as well, side by side. Your repo wants one version. Nothing gets installed, upgraded, or edited while it runs. It only reads and it only prints. That restraint is deliberate, because the instinct during a security scare is to start typing upgrade commands immediately, half-caffeinated, at speed, into the wrong terminal. The actual first skill is knowing what state you're in before you change it. Diagnosis before surgery. So you run the check, and you look at the resolved Ruby, the one your repository actually settles on. If that number is anything below three point three point fourteen, three point four point thirteen, or four point oh point ten, you are looking at the bug, not at a rumor of it. The report doesn't diff anything, it changes nothing, it just tells you the truth about what's running, which during a disclosure is the rarest commodity on the internet. Honesty about your own versions is somehow a premium feature. Once you have the real numbers, the upgrade is unglamorous, which is the good news. Bump the pinned Ruby in your repository's version file to a fixed release. Let your version manager install that patched release. Then run your test suite. Actually run it. Don't just think fondly of it and assume the gods of continuous integration have your back. A Ruby version jump can drag incompatible dependencies along like luggage falling off a roof rack. Confirm your framework and your gems still resolve cleanly. The whole thing is five minutes if nothing breaks, and an afternoon if something does, and both of those outcomes are still cheaper than remote code execution. One caveat for the self-hosted crowd. If you're running Discourse, Mastodon, or any of the other bundled products, do not go swapping the Ruby inside the vendor's packaging yourself. That's their plumbing, not yours, and a hand-rolled runtime swap inside a bundled product is a fantastic way to break updates forever while feeling clever for about ten minutes. Watch for their patched releases, apply those when they ship, and let them manage their own innards. Your job is to know you're affected and to be ready when the fix arrives, not to perform unauthorized surgery on someone else's appliance. The appliance remembers, and it will not forgive. On timing and priority: Rails and Sinatra applications on default configurations go to the front of the line, because the bug is reachable before any authentication, which is security-speak for the exposure starts at the network and works inward. But any Ruby service that keeps untrusted input anywhere near memory deserves the same five minutes of checking. If they come back dirty, you found out today, from a version report, rather than later, from somewhere considerably worse. If you sit behind Cloudflare, the firewall rules are already blocking, free plans included, so you have a bridge while the upgrade lands. But don't confuse the bridge with the far shore. The Ruby team is aware of working proofs of concept, and a filter that never sees a request cannot block anything that travels that request's route. A quick word on what we know versus what we don't, because that line matters in every security story and nobody else is going to draw it for you. What the source establishes: the bug exists in string case conversion, it's rated Critical, proofs of concept achieve remote code execution in some scenarios, the fixed versions are the three I named, and Cloudflare's rules block for everyone. What it does not establish: that anyone has been exploited in the wild, or that your specific application is definitely reachable. The honest move is to check, not to assume in either direction. So here's your one next step, and it's small on purpose. Run the version check against any Ruby project you touch, today, before you decide this is somebody else's emergency. Not next week, not after the backlog, not after the thing you're calling a quick fix. Today. Read the resolved Ruby against the three fixed releases, spelled out one more time for the road: three point three point fourteen, three point four point thirteen, and four point oh point ten. If you're behind, bump, test, upgrade. If you're behind Cloudflare, note the bridge and still patch. Either way, you'll know exactly where you stand, which on any given disclosure day puts you ahead of most of the internet.
