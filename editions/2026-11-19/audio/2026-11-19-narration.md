# GitHub CLI can finally wait for a pull request to change

*The spoken edition of The Working Copy for 2026-11-19. Narrated by Uncle Burt.*

There are two kinds of quiet when you are waiting for someone to review a change. In one, the reviewer has not answered yet. In the other, the reviewer has answered, but the little script on your machine has not asked again. The interesting part is not knowing how to ask faster. It is knowing whether you need to keep asking in the first place. The GitHub command line, from version two point one zero five point zero onward, now offers a different arrangement. The feature lives in a new family of event commands, and the headline one is the event listen command. You give it the address of a pull request and say which change you care about. It sets up a subscription and listens. When the matching event arrives, it prints a record. By default, it stops after the first one. If the next step in your script needs one answer, you can wait for one answer. You do not have to design a miniature reporting service just to find out whether a review came in. Picture a change you have sent to a colleague. The next thing you want to know is whether they have submitted a review. You could open the request now and read its current state. You could also put the same question inside a loop and keep asking until the answer looks different. Now you are trying to learn about a change over time by taking a sequence of pictures. Listening lets you describe that job more directly. With the event listen command, you pick the event for a submitted review, not every event associated with the request. A new change at the head of the request might matter to a build, but it does not tell you that a person has submitted a review. A completed set of checks might matter before a merge, but it is not a review either. Submitted reviews. Changes to the request's state or its head. Merge conflicts. Completed check suites. Choosing among them is a decision about the work, not just a detail of command syntax. Before you decide to change a workflow, though, find out what your workflow actually does. For the written edition of this story, we put together a small local reader. It is a Python script that you run against your own repository checkout. You invoke it with Python and pass it the path to your repository on your machine, and it looks through the GitHub Actions workflow files for lines that use the GitHub command line to inspect a pull request or a run. It reports the file, the line, and the particular check it recognized. It does not start a workflow. The point is simply to give you a place to look. In the little fixture we used to try it, there was one workflow with one matching line, and the script finished with a count of one. That output is an example from a hand-made fixture, and your filenames, your line numbers, and your counts will differ, because your repository is presumably more than one small workflow. It does not tell you how often the check runs. The useful result is the address of a question you can now answer by reading a few lines around it. Suppose those lines show a step that reads the current state once, includes it in a report, and finishes. That step is not waiting for anything. Replacing it with a listener would quietly change the meaning of the report. Instead of telling you what is true when you ask, the new step would wait for something else to happen. You started out looking for unnecessary work, and you would have introduced a delay instead. Mark that match as a deliberate snapshot and leave it alone. Now imagine a different match. This time the surrounding step checks the request, pauses, and comes back to check again. Read the condition that lets it leave. If the answer is that a review has been submitted, you have found something much more specific than a line that mentions a pull request. You know which transition the author was trying to detect. Write that down in ordinary language before you reach for a replacement. If you cannot finish the sentence about what the step is waiting for, you are not ready to change it. There is another decision hiding just after that condition. What should happen if the review does not arrive while the job is allowed to wait? The event listen command has a timeout flag that sets a time limit on how long it waits. That gives your surrounding workflow a way to stop waiting, but it does not make the decision for you. Perhaps the next step must not happen at all. Do not accidentally treat the end of a wait as evidence that the review arrived. Think about the result the next step needs, too. The listener prints each matching event as a line of structured data, and you can use the jq flag or the template flag to ask for particular fields rather than handing every part of that record to whatever runs next. Start with the decision, then work back to the smallest piece of information that supports it. If the next step only needs to know that a review was submitted, avoid designing an elaborate report nobody has asked to read. If it needs to distinguish among results, make that distinction explicit before changing the handoff. One event is the default, not a requirement. The count flag lets you ask for several events, and the follow flag keeps the listener running rather than stopping after the first match. That can make sense for someone watching a request unfold. It is a different choice for a short step that is supposed to finish and hand control back. Think of a doorbell and a conversation. A bell tells you when someone has arrived. A conversation stays open because there is more to hear. Decide which of those your workflow needs before leaving a listener running simply because it can. There is a practical boundary here as well. GitHub says the event commands are in preview and may change, and access to the event streams is itself in preview on GitHub, behind a waitlist you have to sign up for. The announcement says you need version two point one zero five point zero of the command line or later. Finding a likely loop in your files does not show that your account has access. And having access would not, by itself, show that the loop you found should be replaced. You can do the local reading today and keep the proposed change as a note until you can test it in the right setting. One more thing is worth knowing. Existing commands, like the ones that create and view pull requests, view runs, watch runs, and call the API, now suggest the event listen command instead of polling. If you run agents, they may find this on their own, possibly before you do. A useful note is short enough that the person who owns the workflow can disagree with it. Name the step. Say whether it reads a state or waits for a change. If it waits, name the event. Say whether a single occurrence is enough, and say what to do when the allotted time runs out. That is already a better discussion than a broad suggestion to modernize the workflow. Someone reading the note can point to a mistaken assumption without having to undo a change first. If you decide to try the listener, keep the first comparison narrow. Upgrade your command line. Join the waitlist. Use a request where you can observe the event you chose. Look at the record you receive, then look at the condition the old step was meant to satisfy. Ask whether the evidence in that record really answers the same question. A record arriving is something you can observe. Whether it justifies the next action is something you still have to decide. That distinction is where a tidy command becomes a useful workflow rather than a different kind of guess. When you get back to your own repository, run the scan against your own checkout. Start with one matching line, and read what comes immediately before it and what depends on it afterward. Leave a one-time check alone. If it is a real wait, write down the event that would let the next step begin, and write down what should happen if it never arrives. Then give your replacement a timeout, so a stuck stream cannot wedge the pipeline. You will have a small, testable change to consider, or a good reason not to make one. Either is a better outcome than asking the same question again out of habit.
