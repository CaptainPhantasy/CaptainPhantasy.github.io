# GitHub's new PR overview stops optional checks from crying wolf

*The spoken edition of The Working Copy for 2026-11-20. Narrated by Uncle Burt.*

GitHub has been quietly fixing its new pull request overview page, and the headline change is honesty. Failed optional checks used to make a perfectly mergeable pull request look blocked, which trained everyone to ignore red marks, which trained everyone to ignore the actual blockers too. Interfaces that cry wolf get muted, not obeyed. Now the page says what it means. And that makes today a good day to go find the automation in your own repository that stares at pull requests, because clearer status is only useful if you know what's feeding it.

The overview has been in public preview since November fifth, and this update is mostly the sound of GitHub responding to the loudest complaints. The big fix is merge status. Optional checks that fail no longer masquerade as blockers, and missing merge requirements now tell you what actually needs attention instead of radiating vague disapproval. There's also a readiness summary that guides reviewers and visitors, including the case where the correct answer is that nothing needs doing, which may be the first time a status page has dared print that sentence.

The rest of the update is polish, but polish with payoff. Checks and approvals now expand when you click them, instead of pinning a preview to your screen like a barnacle. Overlapping previews and mobile interaction problems got fixed. Resolved review threads collapse, so finished arguments stop haunting your scrollback like ghosts with strong opinions about naming conventions. Anyone who has reopened a thread about indentation that is months old knows exactly what this is worth.

There's more. Activity around force pushes now links to both the old and the new commits, so a reviewer can actually compare what changed instead of performing faith in your claim that it was just a rebase. Commit activity now carries timestamps, so you can see when changes landed instead of reverse-engineering the timeline from vibes. The source and target branches stay visible on smaller screens, and the sidebar lets you edit development links and lock or unlock conversations without leaving the page. If you want to try it, there's a button in the header that opts you into the new overview, and the same menu lets you crawl back to the classic view when nostalgia hits.

GitHub is explicit that this preview is a starting point, not the finished experience, and they're asking what still sends people back to the old page. That's a genuinely useful question, and it's answerable, and the questions get easier to explain when you have read your own automation.

Here's why that matters. The overview reports merge readiness. Our local scanner does not. It finds a narrow set of workflow lines that ask about pull requests or runs. Those are two different views of a repository, and keeping them separate saves us from turning a tiny tool into a very confident liar.

So today's concrete step is a small, narrow, read-only scan you run against your own repository. The accompanying scan takes one input, the location of your local repository. It reads workflow files for matching lines that query a pull request or a run through the GitHub command line, then prints the matching file locations and a candidate count. It reads files and nothing else. It does not execute anything from your repository, it does not suggest edits, and it stops dead at the point where judgment should begin. That restraint is the feature. A match is a place to read, not a verdict, and treating it as a verdict is how repos end up with workflows nobody can explain at three in the morning.

In a small local fixture with a single workflow, the scan reported exactly one candidate: a step in a review workflow that pulls the details of a pull request through the command line tool. One line, one workflow, done. Your output may differ. Perhaps your repository has no matching lines. Perhaps it has more workflow files than anyone can hold in mind. Read the actual filenames, line positions, and counts instead of borrowing the fixture's answer. That's fine. The number isn't the point. The list of places is the point.

Now be clear about what this scan does not establish, because the limits are doing real work here. It does not enumerate your checks. It does not tell you which statuses are required or optional. It does not know anything about your merge rules, your branch protections, or whether you have access to the preview at all. A matching line proves only that somewhere, some workflow step asks the command line tool about a pull request or a run. That's it. It's a flashlight, not an audit, and definitely not a security review.

So what do you do with the matches? You open the step around each one and read it like a human being. What does the step actually do with the pull request data once it has it? Is it fetching details to make a decision, or is it polling in a loop because someone in the distant past was working around a limitation that may no longer exist? These are the questions the scan surfaces and cannot answer. The answering is your job, and it's the part that takes actual thought rather than a command.

The required-versus-optional question is a separate review entirely. Read the actual branch rules and repository settings rather than trying to infer them from this scan. That's where you go to find out what genuinely gates a merge versus what merely runs and complains. This matters more than it used to, because the new overview page draws a sharper line between checks that block and checks that merely sulk. If your settings say a check is optional, the page no longer needs to dress that failure up as a merge blocker. The check may still be telling you something useful; it simply does not get to run the door.

Resist the urge to rewrite a workflow the moment the scan flags it. One matching line is a reason to ask a question, not a reason to refactor before lunch. Maybe the step is load-bearing. Maybe it's vestigial. Maybe it's been vestigial for years and everyone who knows is on a different continent now. Reading in context before deciding is the whole discipline here, and it's the difference between maintenance and archaeology performed with a shovel.

Once you've read your matches and checked your settings, go flip on the preview and open your next pull request. Compare the readiness summary against what you found by hand. If they agree, the page and your reading of the settings line up for that pull request. That is a useful cross-check, not a guarantee about every check. If they disagree, that's not a mystery, that's a finding, and GitHub has explicitly asked for findings like it. They want to know what's easier to find, where you still lose context, and what sends you back to the classic view.

Your next step, then: run the read-only scan against your repository, read each matching step in context, and check your settings for what actually gates merges. Then take one pull request through the new overview and see whether it tells the truth about your setup. If it doesn't, tell them, in the feedback discussion they've set up for exactly this purpose.

Here's a worked example of the judgment part. Suppose the scan hands you a match in a step called get PR details, and when you open it, you find it fetching the pull request and passing the title off to a notification somewhere. That's a read, an innocent one, and the right response is to nod and move on. Now suppose the neighboring step takes that same pull request data and decides, in a shell conditional nobody has looked at since the repo had a different name, whether to mark something green. That one deserves a slow read and a visit to your settings, because the new overview will happily report whatever that step produces as though it were weather rather than opinion. The scan can't tell those two apart. That's not a failure of the tool; that's the boundary where the tool stops and you, regretfully, begin.

That beats the traditional alternative, which is quiet grumbling followed by closing the tab, an approach with a long history and zero fixes shipped.
