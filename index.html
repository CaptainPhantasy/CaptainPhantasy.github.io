GitHub Actions will happily run YAML your parser rejects

There is a small, documented gap between what GitHub Actions accepts in a workflow file and what counts as valid YAML anywhere else. A workflow with malformed structure can be swallowed without complaint, and you only find out when a job silently does the wrong thing in CI.

What's actually going on

YAML, the indentation-and-colons format your workflow files are written in, has a specification. Most parsers enforce it. GitHub Actions, it turns out, accepts workflow files that violate it. That's not a scandal on the scale of, say, a memory-corruption bug — it's more like a restaurant that serves you food the health inspector wouldn't. Nobody dies, but you shouldn't assume the kitchen is checking anything.

The practical consequence is the illusion of validation. Your workflow runs, green checkmark and all, so you assume the file is well-formed. But a structurally invalid file that GitHub tolerates can misbehave in ways that look like logic bugs: a condition that never fires, a step that gets skipped for reasons the UI won't explain. You'll debug your logic long before you think to question the file itself.

The habit: check with something other than GitHub

The fix is to stop treating GitHub's acceptance as a correctness signal. If GitHub's parser is the forgiving one, your check has to come from a stricter one. The general move: run your workflow files through a strict YAML parser or a dedicated workflow linter of your choosing, locally, before you push. Any tool whose entire job is to say "no" to malformed YAML will do — the point is that it is not the same program that runs your pipelines.

Here's the worked example. Say you edited a deploy workflow and GitHub accepted it, but the deployment job started skipping itself. Before you spiral into debugging your logic, take that workflow file and parse it with a strict, standards-following YAML library — the kind shipped with your language's package manager. If the file contains something like a duplicated key where the second quietly overwrites the first, or indentation the specification forbids, a strict parser will complain where GitHub shrugged. You get a line number instead of a mystery. Fix the line, re-parse until it's clean, then push. The loop is faster than one wasted CI run.

If you want this to be a team habit rather than a personal one, make the strict parse a first step in CI itself, so a pull request with malformed workflows fails loudly at the lint step instead of failing mysteriously three jobs later. Either way, the principle holds: the thing that runs your code should not also be the only thing that checks its own configuration.

Why it matters

  • A workflow file GitHub accepts can still be structurally invalid YAML, so a green run is not proof your config is sound.
  • Strange CI behavior — skipped jobs, conditions that never fire — can come from file structure, not your logic.
  • Parsing your workflows with a strict local tool catches these before you burn a CI run or a teammate's afternoon.

Hand it to your agent

Here's a prompt you can hand to your coding agent. It will read your workflow files and look for the kind of structural sloppiness GitHub tolerates but strict parsers don't — things like duplicated keys and off-spec indentation. It reports what it finds and stops before changing anything, so you decide what to fix.
