# RHEL runners go GA, so your CI can match what you ship

*The spoken edition of The Working Copy for 2026-11-22. Narrated by Uncle Burt.*

Red Hat Enterprise Linux runner images for GitHub's hosted larger runners have gone generally available, which is the software industry's way of saying the training wheels are off. The preview that began in June, in partnership with Red Hat, is now fully supported for production workflows in GitHub Actions. Translation: if your deployment target is Red Hat, your continuous integration no longer has to approximate the operating system you actually ship to. It can just be that operating system. A radical idea, apparently. The phrase that matters here is fully supported for production. Preview badges exist so vendors can hedge quietly while you discover the edges on their behalf. That badge is now gone from these images, which means somebody is on the hook when things break, which is the actual difference between a preview and a product. It's the difference between borrowing a friend's van and renting one with insurance. Same van, very different feeling when the radiator complains. There are two honest use cases buried in the announcement, and they're worth separating. The first: run your workflows on the same operating system you deploy to, so the thing that passed your tests resembles the thing receiving your software. The second: use these images as a foundation for custom images that carry your own tools, dependencies, and configuration. Bake once, run anywhere within reason. Both are legitimate; knowing which one you want saves you from building a custom image to solve a problem the base image already handles. Now the catch, because there is always a catch and pretending otherwise is how press releases work. These images are available for larger runners on the Team and Enterprise Cloud plans. If you're on the free tier, this is a spectator sport. You can read about the parity; you cannot have it. That's not a scandal, it's a pricing page, but it does mean the first question for any team is not technical. It's whether your plan includes the seat at the table. Getting started, should you qualify, is refreshingly blunt. Create a new Linux sixty-four-bit larger runner and pick your Red Hat image from the partner images section. That's the whole ceremony. And if you were already using the preview, nothing breaks. Existing runners and workflows continue as they are, no migration ritual, no incantation, no weekend of rewriting labels. The upgrade, in this one instance, is simply the passage of time. Savor it. It doesn't happen often. But creating the runner was never the hard part. The real work is figuring out which of your workflow files deserve the edit. Most repositories accumulate workflows the way garages accumulate cables: some are load-bearing, some are vestigial, and nobody remembers which is which. Every repository has that one workflow named after a person who left in a previous administration. Before you touch runner labels, you want a shortlist of files actually worth opening, and you want it without reading everything by hand until your eyes glaze. That's what the accompanying script does. You run it against your own repository checkout, pointing it at the directory, and it walks your workflow files looking for lines that check on a pull request or invoke the GitHub command line tool. When it finds one, it prints the file and the line number so you can go straight to the spot. It reads files and executes nothing. It won't run a workflow, won't run a command from your repository, and won't volunteer opinions. It is a reading aid, not a butler. To show what the output looks like, I ran it against a small local fixture containing a single workflow. It reported one matching line — a GitHub command-line call that views a pull request, in the review workflow at line four — and a candidate count of one. That's the whole result. Now, the honest framing: that output comes from my little test setup, not from your repository. Your filenames, your line numbers, and your counts will differ, because your repository is not my fixture. Mine is a broom closet; yours is presumably a house, possibly with an attic. You might reasonably ask why a runner-label inventory starts with pull-request checks. Fair question. Those lines mark the workflow files humans actually watch — the ones whose names show up on every pull request, patiently waiting for a green tick before anyone merges anything. Those are exactly the files you'll be opening anyway to inspect runner labels. The scan just gets you there without the archaeology. It connects the files people look at to the files you need to edit, which turns out to be the same set. One caution worth stating plainly, because a tool that oversells itself is just a shrug with a subscription attached. A match is a place to look, not a verdict. It is not proof that a job is compatible with Red Hat images, not proof of anything about polling behavior or tooling support, and it is definitely not a security audit. It's a structural read of text files. One matching line is an invitation to ask a question, not a reason to rewrite a workflow on a Friday afternoon. So here's the move. Take the shortlist the scan hands you, open those files, and look at the runner labels pinned in each job. Then ask the honest question per job: does this genuinely need Red Hat fidelity, or did it inherit its label from a copy-paste three maintainers ago, back when nobody asked because it worked? Inheritance is not architecture. The jobs that actually deploy to Red Hat are your candidates; the rest can keep doing whatever they've been doing. For the candidates, the path is short. Create a Linux larger runner and choose the Red Hat image from the partner section, or start from that image when building a custom one with your tools baked in. GitHub's documentation on managing larger runners and on using custom images covers the remaining details, and it does so without requiring you to infer anything from a changelog written in a hurry. The wider point is modest but real. Testing on the operating system you deploy to used to mean keeping a self-hosted box alive — patching it, babysitting it, explaining to it that the update really was mandatory. Now, for teams on the right plans, that box can retire. Parity between your pipeline and your production environment stops being an aspiration and becomes a menu option, which is less romantic and considerably more reliable. Your next step is the inventory. Run the scan against your repository, get your shortlist, and make one decision per job about whether it needs the new images. That's it. No big-bang migration, no flag day, just a quiet set of edits where they matter. Here's a concrete walk through the decision, because the shortlist only earns its keep when you act on it. Say the scan hands you a match in a review workflow — the kind of file whose name shows up on every pull request, waiting for its green tick. That file goes to the top of the pile, and for one very ordinary reason: it's the one place where a runner change will be noticed immediately if it goes sideways, because every maintainer stares at it on every merge. Change a label in a workflow nobody watches and the failure mode is a mystery discovered weeks later by whoever lost the coin flip. So you open the file, find where the job declares which machine it runs on, and then you sit with the question that actually matters. Does this job ship software to Red Hat, or does it just check a pull request and report back? If it's the latter, moving it buys you nothing except the warm feeling of consistency, which is not a deployable artifact. If it touches the operating system you deploy to — installs packages, exercises system tooling, anything where the difference between distributions is the difference between works and doesn't — that's your candidate. That's the whole judgment, and no script can make it for you, because the script can't see your production environment. Neither, for that matter, can the announcement, which is why it offers two use cases instead of one prescription. The quiet trick is that this scales by subtraction. Most jobs will fail the does-it-need-this test, and they should — they keep their inherited labels and their unglamorous lives. What's left is a handful of edits in the files people actually watch, which is exactly where you want your changes when a new image is involved: visible, small, and reversible before anyone merges anything they'll regret. And if you were on the preview all along, your step is even shorter: enjoy doing nothing, correctly, for once.
