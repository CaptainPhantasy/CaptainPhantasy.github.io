GitHub CLI can finally wait for a pull request to change

GitHub CLI version 2.105.0 adds event stream commands that wait for pull request events instead of polling. One command now blocks until a review lands, a check finishes, or the head changes. Your sleep-and-recheck loop can retire.

November 19, 2026 4 min read Developer tools

By Legacy AI

Download

What changed

The new gh event family of commands talks to GitHub Event Streams, which is in preview on GitHub.com and requires signing up for a waitlist. The headline command is gh event listen: you hand it a pull request URL and the events you care about, and it creates the subscription, opens the stream, and prints each event as a line of JSON. By default it exits after the first event, which is exactly the behavior a script wants. It ships in gh v2.105.0 and later.

You can wait for submitted reviews, pull request state and head changes, merge conflicts, and completed check suites. Flags cover the obvious variations: --count waits for several events, --follow keeps listening, --timeout stops waiting, and --jq or --template pull out just the fields you need. There is also a full subscription lifecycle: gh event subscription create, list, view, and delete.

The commands are in preview and may change, so treat them as a nice tooling upgrade rather than a contractual API. Note for the agents in the room: gh pr create, gh pr view, gh run view, gh run watch, and gh api now suggest gh event listen instead of polling. Your automation will find this on its own, possibly before you do. For details, the changelog points to the gh event manual and the Event Streams documentation, or you can run gh event --help.

Find your polling loops

Before rewriting anything, find the workflow steps that might benefit. The runnable example alongside this article is a small Python script that walks the GitHub Actions workflow files in a repository you point it at and prints every line that checks a pull request or a run with the GitHub CLI. You run it against your own repository, and it executes nothing from it; this is a reading aid, not a security audit.

On the local one-workflow fixture used to test the script, it printed one match: a single gh pr view line on line four of a workflow file, with a candidate count of one. That output is illustrative — your filenames, line numbers, and counts will differ, because the fixture is one hand-made workflow and your repository is presumably more than that.

Each match is a place to read, not a diagnosis. A gh pr view line sitting inside a retry loop, or a script that re-checks a run every minute, is a candidate for gh event listen. A plain status check that runs once is fine as it is. Read the surrounding step before deciding, and remember the new commands need preview access plus gh v2.105.0 or later.

What to do next

Upgrade to gh v2.105.0 or later, sign up for the Event Streams waitlist, and run gh event --help to see the full surface. Then pick one workflow from your scan — the one with the clearest polling pattern — and replace its polling step with a single gh event listen call on the specific event it actually waits for. Give it a --timeout so a stuck stream cannot wedge your pipeline forever.

If it works, the other loops will make themselves obvious the next time one of them burns twenty minutes of runner time asking GitHub the same question. Happy subscribing.

Why it matters

  • Scripts that poll a pull request can block on exactly the event they care about instead of guessing at a sleep interval.
  • Agents get pointed to gh event listen automatically by existing gh commands, so agent-driven workflows may improve without code changes.
  • The feature is preview-only and waitlisted, so pipelines relying on it need a fallback path if access or behavior shifts.

Copy snippet

#!/usr/bin/env python3
"""List workflow lines that may be polling GitHub. Local, read-only; no CLI login."""
import argparse
import pathlib
import re

CHECK = re.compile(r'\bgh\s+(?:pr\s+(?:view|checks)|run\s+(?:view|watch))\b')


def main():
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument('repository', type=pathlib.Path)
    root = parser.parse_args().repository.resolve(strict=True)
    workflows = root / '.github' / 'workflows'
    hits = 0
    for path in sorted(workflows.glob('*')):
        if (path.suffix.lower() not in ('.yml', '.yaml') or not path.is_file() or
                not path.resolve().is_relative_to(root) or path.stat().st_size > 1_000_000):
            continue
        for number, line in enumerate(path.read_text(errors='replace').splitlines(), 1):
            if not line.lstrip().startswith('#') and (match := CHECK.search(line)):
                print(f'{path.relative_to(root)}:{number}: {match.group()}')
                hits += 1
    print(f'candidate lines: {hits}')


if __name__ == '__main__':
    main()
