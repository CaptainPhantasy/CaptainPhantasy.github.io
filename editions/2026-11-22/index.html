RHEL runners go GA, so your CI can match what you ship

Red Hat Enterprise Linux 9 and 10 images for GitHub-hosted larger runners left public preview on November 19 and are now fully supported for production workflows in GitHub Actions. If your deployment target is RHEL, your CI no longer has to guess what "close enough" means.

November 22, 2026 4 min read Developer tools

By Legacy AI

What actually changed

RHEL 9 and RHEL 10 images for GitHub-hosted larger runners are now generally available, after a public preview that started in June 2026 in partnership with Red Hat. "Fully supported for production" is the operative phrase: preview badges are where confidence goes to be quietly hedged, and this one is gone.

There are two honest use cases in the announcement. Run your workflows on the same operating system you deploy to — a radical idea, apparently — or use the RHEL images as the foundation for custom images carrying your own tools, dependencies, and configurations. The catch, because there's always one: RHEL images are available for larger runners on GitHub Team and GitHub Enterprise Cloud plans. If you're on Free, this is a spectator sport.

Getting started is refreshingly blunt: create a new Linux x64 larger runner and pick your RHEL image under partner images. And if you were already on the preview, nothing breaks — existing runners and workflows continue as-is, no migration ritual required.

Shortlist the files worth opening

The real work of adopting this isn't creating the runner; it's figuring out which of your workflow files deserve the edit. Most repositories accumulate workflows the way garages accumulate cables: some are load-bearing, some are vestigial, and nobody remembers which is which. A structural scan beats opening each one by hand and hoping your eyes don't glaze over.

The script accompanying this edition, find-pr-checks.py, runs against your own repository checkout: python3 find-pr-checks.py /path/to/your/repo. It walks your workflow files and prints any line that checks a pull request or runs the GitHub CLI, with file and line numbers attached. As an illustrative example, on a local one-workflow fixture the output was a single match — a gh pr view call in review.yml at line four, with a candidate count of one. To be clear, that output is an example from a small local test, not a run against your repository; your filenames, line numbers, and counts will differ, because your repository is not my fixture. Mine is a broom closet; yours is presumably a house.

Why pull-request lines, when the goal is a runner-label inventory? Because they mark the workflow files where humans actually look at checks — the files whose names appear on every PR waiting for a green tick. Those are the same files you'll be opening to inspect the runs-on labels and decide which jobs move to a RHEL image. Treat each match as a question, not a verdict: the script reads files and executes nothing from your repo, and a match is not proof a job is compatible with RHEL images. It's a reading aid that hands you a shortlist, not a migration consultant.

What to do next

Take the scan's shortlist, open those files, and look at the runner labels pinned there. Ask the honest question per job: does this genuinely need RHEL fidelity, or did it inherit a label from a copy-paste three maintainers ago? The ones that deploy to RHEL are your candidates.

For those, create a Linux x64 larger runner and choose the RHEL image under partner images, or start from RHEL for a custom image with your tools baked in. GitHub's docs on managing larger runners and using custom images cover the rest. One scan, one decision per job, and your CI finally resembles your production environment instead of a cousin of it.

Why it matters

  • Jobs that deploy to RHEL can now test on the same OS without maintaining self-hosted runners.
  • Existing preview users need to change nothing — workflows keep working as-is through the GA transition.
  • RHEL images require larger runners on Team or Enterprise Cloud plans, so plan-tier constraints decide who gets parity.

Copy snippet

#!/usr/bin/env python3
"""List workflow lines that may be polling GitHub. Local, read-only; no CLI login."""
import argparse
import pathlib
import re

CHECK = re.compile(r'\bgh\s+(?:pr\s+(?:view|checks)|run\s+(?:view|watch))\b')


def main():
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument('repository', type=pathlib.Path)
    root = parser.parse_args().repository.resolve(strict=True)
    workflows = root / '.github' / 'workflows'
    hits = 0
    for path in sorted(workflows.glob('*')):
        if (path.suffix.lower() not in ('.yml', '.yaml') or not path.is_file() or
                not path.resolve().is_relative_to(root) or path.stat().st_size > 1_000_000):
            continue
        for number, line in enumerate(path.read_text(errors='replace').splitlines(), 1):
            if not line.lstrip().startswith('#') and (match := CHECK.search(line)):
                print(f'{path.relative_to(root)}:{number}: {match.group()}')
                hits += 1
    print(f'candidate lines: {hits}')


if __name__ == '__main__':
    main()
