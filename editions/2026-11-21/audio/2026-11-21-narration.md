# Azure DevOps migrations now keep working while you keep working

*The spoken edition of The Working Copy for 2026-11-21. Narrated by Uncle Burt.*

GitHub has flipped the switch on its enterprise live migration service from Azure DevOps, announcing its general availability. The pitch is simple enough to fit on a moving box: your repositories sync continuously to GitHub Enterprise Cloud with data residency while your teams keep working, and when you're ready, you cut over on your own schedule. The tool even validates things before the move and tracks the migration's lifecycle as it runs. It's the rare platform migration that treats downtime as a bug rather than a personality trait, and for anyone who has lived through a weekend-long freeze while two systems argued about history, that alone is worth a quiet nod of respect.

So what actually comes along for the ride? According to the GitHub changelog, the migration carries your full Git history, your branches, your tags, and your pull requests — and not just the pull requests as empty shells, but their titles, descriptions, comments, and the user history attached to them. That last part matters more than it sounds. Migration tools have a long tradition of moving the furniture and losing the movers, leaving you with a wall of comments attributed to nobody in particular. This one at least claims to keep the receipts, which is the difference between a repository and a very organized junk drawer.

The branch policies are where it gets interesting in the "could be great, could be a puzzle" sense. Your Azure DevOps branch policies arrive on the GitHub side as branch rulesets, automatically translated. That's either a week of clicking you don't have to do, or a ruleset you'll spend a week deciphering, trying to remember which of your former colleagues configured it and what they were angry about at the time. Probably both, if we're honest. Governance migrates whether anyone remembers how it was configured, which is convenient and slightly ominous in equal measure — like inheriting a filing cabinet where all the labels are correct and none of them are explained.

Two details in the announcement earn genuine respect. The first is that developers keep contributing throughout the migration. The sync runs continuously from the old system to the new one, so nobody has to stop committing while the machinery hums in the background. That does not abolish the brief final cutover or the need to plan it. It does mean the bulk of the move need not begin with telling the whole team to stop contributing. The second is flexibility in how you drive it: there's a guided experience in the Azure DevOps portal if you like being walked through things, or a scripting path if you'd rather encode the whole operation and never look at a wizard again. Both flavors come with pre-migration validation and lifecycle tracking, which surface problems before cutover instead of during it, when they're traditionally much more expensive and much more public.

Now the asterisk, because there's always an asterisk. Azure Boards and Azure Pipelines stay put. The migration can create the Boards connection and rewire your pipelines to point at the newly moved repository, which does reduce the manual fiddling after cutover. But your work items and your pipeline definitions remain in Azure DevOps for this migration, presumably humming softly to themselves. Half the house moves; the plumbing bill stays behind. So the realistic end state isn't a clean break — it's a split-brain setup where your code lives on GitHub and your boards and build definitions live in their old home, connected by a wire both parties are politely maintaining. Plan for that from day one and you'll spare yourself the discovery later.

Here's the thing about a live migration, though, and it's the part nobody schedules: the experience is only as pleasant as the repository it carries. The announcement describes continuous sync from Azure DevOps to GitHub, not a two-way exchange. And a local checkout is not the same thing as repository history: it can contain untracked material, while a small inventory also skips some directories. The inventory is a place to start reading, not a packing list certified by the migration service. So before you schedule anything, it's worth knowing exactly what's in the box you're about to ship. That's not a security audit. It's reading the label before you lift.

The way to do that is a structural inventory, and it takes about a minute. We've been running a small read-only script for exactly this: it walks the repository tree and tells you what's actually in there. An inspection tool that edits your repository has badly missed the assignment. You point it at any local repository — yours, a colleague's, that one project everyone's afraid of — and it produces a plain report you can actually reason about before anything syncs anywhere.

The report covers a handful of useful angles. It counts the files and shows you the top-level layout, so you know the shape of the place. It reads the documentation's headings, which tells you whether the project explains itself or just gestures vaguely at a folder. It tallies languages by file extension, which is often more honest than anyone's memory of what the codebase is written in. And it ranks the largest source files, because bulk is a migration cost even when the tools are polite about it. Think of it as a mover walking through your garage with a clipboard before quoting you a price.

On a small local test repository, the script counted four files in total. The top-level entries included a readme, package metadata, a source directory, and a tests directory. It found the readme's headings — a project title and a getting-started section, which is more documentation discipline than many projects manage. The language tally came out as two Python files, one markdown file, and one file of package metadata. And the largest-files ranking put the readme on top, followed by a test file, the metadata, and a tiny source file. Your output will differ, and that's not a disclaimer, that's the entire point — the value is in running it against your repository, not trusting anyone else's.

Because here's what the example can't establish, and it's worth being blunt about. This is a structural read, nothing more. It does not inspect dependencies, so a hypothetical package that phones home at build time is not something it can diagnose. It doesn't examine build scripts or runtime behavior, so whatever your pipeline actually executes is beyond its reach. And it is absolutely not a security review — file names tell you what things are called, not what they do. The report is a map of the terrain, not an inspection of the bridges. Anybody who treats a directory listing as due diligence is going to have an educational quarter.

What you do with the answer is the part that saves you. Look at the inventory the way a mover looks at your garage: anything surprising should be surprising now, not on cutover day. Suppose you notice an unexpectedly large file, readme names that deserve a comparison, or a directory whose purpose you need to ask about. Those are reading questions, not conclusions the inventory has already established. All of these are cheap to confront before you decide which tracked repository content will travel from Azure DevOps to GitHub. After cutover, they're just… features of your new home.

Once the inventory looks sane, the actual path forward is straightforward. Read Microsoft's migration documentation — the changelog points there as the starting line, and it covers both the guided portal experience and the scripting route. Run the pre-migration validation, which is exactly the kind of unglamorous check that pays for itself the first time it flags something before the whole company is watching. Then pick a cutover time that works for your teams, because the changelog is explicit that the brief final cutover happens on your schedule, not the tool's. The tool waits. You decide. It's almost suspiciously civilized.

The honest summary is not that every team should move because a changelog has a fresh coat of paint. This is a migration option: continuous sync in one direction, a brief scheduled cutover, translated branch policies, and work items and pipeline definitions that remain in Azure DevOps. What's left is the work that was always yours anyway: knowing what you own, deciding what deserves the trip, and being the person who checked before the moving truck arrived rather than the person who found out during unloading.

Your next step is small and immediate: run a structural inventory of your own repository today, before any of this becomes urgent. Point a read-only tool at it, read the report, and see whether anything surprises you. Surprises are cheaper this week than they'll ever be again. The migration itself is designed to be boring — doing the inventory first is how you keep it that way, and boring, in the context of platform moves, is the highest compliment available.
