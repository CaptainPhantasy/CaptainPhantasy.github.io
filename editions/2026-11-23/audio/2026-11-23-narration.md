# GitHub Actions will happily run YAML your parser rejects

*The spoken edition of The Working Copy for 2026-11-23. Narrated by Uncle Burt.*

There's a small, documented gap between what GitHub Actions accepts in a workflow file and what counts as valid YAML anywhere else on this planet. Your workflow file — the indentation-and-colons document that describes your pipeline — can be structurally malformed, and GitHub will swallow it without a word of complaint. Everything looks fine. The green checkmark appears. Then a job quietly does the wrong thing, and you spend an afternoon debugging logic that was never the problem. Today we're walking through what's going on, how to check for it yourself, and why the fix is mostly about learning not to trust the kitchen that serves you. First, the shape of the problem. YAML — the format your workflow files are written in — has a specification. If you hand a malformed file to a strict parser, it complains. GitHub's parser, it turns out, does not. It accepts workflow files that violate the specification. It's more like a restaurant that serves you food the health inspector wouldn't touch. Nobody dies. Let's be clear about severity before anyone reaches for the incident channel, because this is a story about annoyance, not catastrophe. This is not a memory-corruption bug. It is not a security hole. It's a parser being forgiving in a place where the specification is strict. The danger here isn't that GitHub rejects your file. It's that it accepts it. Acceptance feels like validation. It isn't. A structurally invalid file that GitHub tolerates can misbehave in ways that look exactly like logic bugs: a condition that never fires, a step that gets skipped for reasons the user interface will not explain, no matter how long you stare at it. You'll debug your logic long before you ever think to question the file itself. That ordering is the expensive part. That's the trap worth naming out loud: the illusion of validation. Your workflow runs. There's a green checkmark next to your commit. So you assume the file is well-formed. Why wouldn't you? But the thing doing the accepting is the same forgiving parser that will later misinterpret your structure. So the green checkmark is really just a shrug wearing a pipeline as a costume. It means the run happened. That distinction is the entire lesson, and it's cheap to learn now rather than later. Now, what can we actually establish from the source here, and what can't we? The original write-up documents that GitHub Actions accepts workflow files that violate the YAML specification. That's the concrete claim, and it's solid. What the source does not do is catalog every failure mode you might hit, or promise that any particular weird CI behavior you've experienced over the years came from this. So treat the specific symptoms — the skipped jobs, the dead conditions — as the kind of thing that can happen, not a guarantee of what did happen in your case. The honest position is this: the gap exists, it's documented, and if your CI is being strange, file structure belongs on your list of suspects. Not at the top of the list. On the list. Here's the habit that fixes it: stop treating GitHub's acceptance as a correctness signal. If GitHub's parser is the forgiving one, your check has to come from a stricter one. The general move is simple. Before you push, run your workflow files through a strict YAML parser, or a dedicated workflow linter of your choosing, locally, on your own machine. Any tool whose entire job is to say no to malformed YAML will do. The point isn't which tool you pick. The point is that the checker is not the same program that runs your pipelines. You wouldn't let the chef also be the health inspector, and this is that situation, but with fewer hats involved. Let's walk through the worked example from the page, because concrete beats abstract every time. Say you edited a deploy workflow. GitHub accepted the edit — no complaints, no red marks, nothing. But after you pushed, the deployment job started skipping itself. Not failing. Skipping. Which is somehow worse, because there's no error message to search for, just a job that quietly decided it had somewhere else to be. Your instinct is to dig into the logic: the conditions, the environment settings, the flags you flipped last week and half remember. Resist that instinct for five minutes. Just five. Instead, take that workflow file and parse it with a strict, standards-following YAML library — the kind shipped with your language's package manager, the one you'd reach for with any other configuration file without thinking twice. If the file contains something like a duplicated key, where the second occurrence quietly overwrites the first, or indentation the specification forbids, the strict parser will complain in exactly the place where GitHub shrugged. And here's the beautiful part: you get a line number instead of a mystery. A line number! In this economy! Fix the line, re-parse until it comes back clean, then push. That loop is faster than one wasted CI run, and considerably faster than the emotional journey of debugging logic that was never broken in the first place. Why does a duplicated key cause a skipped job? Think about what a duplicate actually means: two values competing for the same name, and one of them silently winning. If the winning value is the wrong one — say, an older condition, or a setting you genuinely believed you'd replaced — then the pipeline runs with configuration you didn't intend. GitHub doesn't warn you, because its parser never considered it a problem. The strict parser considers it a problem immediately, because overwriting data without telling anyone is, in the specification's opinion, a problem. The specification is right about this. Rarely has a document about indentation been so wise. Now, doing this yourself is good. Making it a team habit is better, mostly because habits survive vacations and one doesn't. The page suggests making the strict parse a first step in CI itself — a lint job that runs before anything else. That way, a pull request containing malformed workflows fails loudly, at the lint step, with a line number and a clear message, instead of failing mysteriously three jobs later when nobody remembers what the pull request even touched, or possibly that they wrote it. The economics are straightforward: one cheap early failure versus one expensive late one, plus the teammate's afternoon you'd otherwise be spending as the debugging budget. Protect the afternoon. The teammate is doing their best. There's a principle hiding in all this, and it generalizes well beyond YAML: the thing that runs your code should not also be the only thing that checks its own configuration. Whenever the executor and the validator are the same forgiving program, you've built a system where errors can pass as success, which is a sentence that should make anyone slightly nervous. You see this pattern elsewhere in developer life — the formatter that's also the linter, the database that accepts whatever you hand it with a smile — and the fix is always the same shape. Introduce a second opinion from something whose only job is to disagree. Disagreement, in tooling, is a feature. A word on tone, because it matters: this is not a reason to panic-audit your entire organization tonight. Most of your workflow files are probably fine, in the way most restaurant kitchens are probably fine. The risk concentrates where files get edited often — the deploy workflow everyone touches, the one with a dozen sets of fingerprints on it and a duplicated key waiting patiently in there since spring. That's where forgiveness turns into sabotage. If you're going to check anything, check the files with the most fingerprints on them. The pristine ones can wait. They usually earn their smugness honestly. So, to recap what we actually know. GitHub Actions accepts workflow files that violate the YAML specification — that's documented in the source, and it's the load-bearing fact. Strict local parsing catches the structural problems — duplicated keys, off-specification indentation — before they cost you a CI run and a chunk of your week. And what we can't establish from the source is that any specific weirdness you've experienced was caused by this. It's a suspect, not a conviction. Your next step is small and concrete. Pick your most-edited workflow file — the one with the most fingerprints, the one you've been side-eyeing for a while now — and parse it with a strict YAML library this week. If it passes, you get to feel smug, briefly and privately, which is the correct amount. If it doesn't, you found a bug before CI did, which is the second-best feeling in software, right behind the line number. Either way, you'll have replaced a shrug with an answer. That's a good trade, and it costs about five minutes. Go spend them.
