# Your laptop can run a coding model now, and the fallback is free

*The spoken edition of The Working Copy for 2026-11-24. Narrated by Uncle Burt.*

There is a quiet change in local coding models that most of the coverage has missed. The stories are still about the biggest model, the newest benchmark, and the workstation with a hundred and twenty-eight gigabytes of memory. That is not the machine most of us own. The useful change is smaller: a coding model that is good enough to fall back on now fits on a gaming laptop or a thirty-two gigabyte Mac, and it costs nothing per token. Start with what got small. Prism ML released a ternary version of a twenty-seven billion parameter model called Bonsai two. Ternary means the weights are stored in three values instead of the usual sixteen bits. The file is five point nine five gigabytes, or seven point two one for the slightly larger build, and the company says it keeps about ninety-eight percent of the base model's score. JetBrains released Mellum two point one Thinking, a twelve billion parameter mixture of experts. Only about two and a half billion parameters are active for each token, and the four-bit build is eight point zero seven gigabytes. Then there is Qwen three point eight twenty-seven B, a dense twenty-seven billion parameter model with a very long context, and a four-bit build around seventeen gigabytes. Those are the three headlines. The wider field matters just as much. OpenAI's GPT OSS twenty B is a twenty-one billion parameter mixture of experts, released in a native four-bit format at about fourteen gigabytes. Mistral's Devstral Small two is a twenty-four billion parameter coding agent at twelve point seven six gigabytes in its smaller four-bit build, or fourteen point three three in the standard one. Qwen three Coder thirty B is a mixture of experts with three point three billion active parameters, and its four-bit file is about eighteen gigabytes. Gemma four comes in a twenty-six billion mixture of experts at about seventeen gigabytes, and a thirty-one billion dense model at eighteen point three two. All of these are open weight, and most are Apache two point zero. None of them is a frontier model. That is the deal. You give up the top of the benchmark table and the largest context windows. What you get is a model that runs without a network, keeps your code on your machine, and does not send a bill. For a fallback, that is usually the right trade. The number that matters is not the parameter count. It is memory. A model has to fit three things: the weight file, the key-value cache that grows with context, and the runtime's own overhead. This is where the thirty-one billion Gemma gets interesting. Its four-bit file is eighteen point three two gigabytes. On a twenty-four gigabyte card that looks fine, until you remember the runtime needs a couple of gigabytes and the context needs its own room. At thirty-two thousand tokens the cache alone is about three point nine four gigabytes. The total runs past the card. The same model that feels comfortable at four thousand tokens is unusable at thirty-two thousand. Context is a budget, not a free setting. There are two kinds of memory. A discrete graphics card has its own video memory. The model must fit there, or the runtime spills layers into system memory and the speed falls apart. Apple silicon shares one pool between the processor and the graphics processor, so a thirty-two gigabyte Mac is a thirty-two gigabyte budget with the operating system on the same bill. Either way, leave two or three gigabytes for the desktop, the editor, and the browser tab that is playing music. Quantization is the other dial. A four-bit file is roughly a quarter of the sixteen-bit size, and the quality loss is usually small. A ternary build goes further. Smaller is not automatically better. A two-bit build of a large model can lose more than a four-bit build of a smaller one. Pick the largest file that fits with a couple of gigabytes left over, and shorten the context before you shrink the model. That order matters. So the exercise is simple. Measure the machine. Pick the largest model that fits with headroom. Give it a context you can afford. Then test it on your own work. The page next to this audio has a fit table where you choose your memory and your context and see which models still fit. The table is a rule of thumb, not a promise. It adds two gigabytes for the runtime and a reserve for context, and it tells you when a model is comfortable and when it is only tight. When you are ready to set it up, start with the runtime, not the model. Ollama is the shortest path. llama dot cpp gives you more control. LM Studio gives you a window and a button. Pull one of the smaller builds first, either Bonsai two or Mellum two point one, and run a real task from your own work. Ask it to explain a function in your repository, write a test for a bug you already fixed, or review a diff. Do not judge it on a riddle. Measure what you got. Note the tokens per second, the time to the first token, and whether the fan or the battery makes the experience unpleasant. Then wire it into your editor as a fallback. Test the failure path. Turn off the network. Switch to the local model. Finish one small task. A fallback you have never used is not a fallback; it is a hopeful setting. Keep the cloud model as the primary and the local one as the seatbelt. Use the local model for private code, offline work, rate-limit days, and the tasks where a slightly weaker answer is fine. Do not pretend it is the same model. The value is not that it beats the frontier. The value is that it is yours, it is free, and it still works when the API does not.  Here is the part most guides skip: the number on the box is not the number you get. A sixteen gigabyte card does not give sixteen gigabytes to the model. The display server, the browser, the editor and the operating system all take a share. On a laptop, the same memory is shared with the processor, and the graphics driver reserves its own slice. Budget two gigabytes for the runtime and another two for the context before you choose a file. If the file is fourteen gigabytes, a sixteen gigabyte card is already full. That is why a fourteen gigabyte model is a twenty-four gigabyte recommendation in practice, and why the ten-gigabyte class is the honest starting point on a sixteen gigabyte machine. The test task matters as much as the model. Pick something small, specific and yours: a function with a confusing name, a failing test you already understand, or a pull request you have been avoiding. Ask for one change, run the tests, and read the diff. A model that writes a plausible paragraph about your code but cannot produce a correct diff has not passed. A model that produces a boring, correct diff has. Keep the prompt short; the local model has less room for a long conversation than the cloud model you are used to. Also decide what the fallback is for. If it is for privacy, run it with the network off and confirm the editor never calls the cloud. If it is for cost, track the days you use it and the bill you avoid. If it is for resilience, unplug the network during a real task and finish it. A fallback with no job is a hobby. A fallback with one job is infrastructure. There is one more habit worth keeping. Write down which model you installed, which file, which context, and what speed you measured. When the next release arrives, and it will, you will not have to start from zero. You will know your machine's budget, and you will know which row of the table is yours. That is the whole change. The local coding model stopped being a workstation hobby. It fits on the laptop you already own. The only thing left is to measure the machine, pick the file that fits, and test it before the day you need it. Go find your memory number. Then find the model that leaves you room to think.
