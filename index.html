When the AI writes the code, the evidence is what you actually read

A new post on the Stack Overflow blog asks a question a lot of us have been quietly avoiding: when an AI writes the code, what counts as evidence that it works? The old habit — glance at the diff, trust the vibes, ship — was shaky even when a human wrote every line. Now the code arrives faster than you can read it, and "it ran once" is doing a lot of load-bearing work.

The question is older than the tools

The post, published on the Stack Overflow blog on November twenty-fifth, frames the problem plainly in its title: when AI writes the code, what counts as evidence? Notice what the question assumes. It assumes that generated code is not self-certifying. A green test run, a successful build, an assistant that says "done" — none of those are evidence in the way a careful reviewer would accept from a colleague. They are outputs, and outputs can be convincing without being correct.

Here is the part nobody puts on the box: this was already true. Code review has always been a claim about evidence — "I read this, and here is why I believe it does what it says." What changed is throughput. When code arrives faster than you can read it, your reading becomes the bottleneck by design, and the temptation is to skip the reading and call the skipped reading a workflow improvement. The honest move is to make your reading cheaper and more targeted, not to stop doing it.

Make the read cheap: three questions per repository

The post supplies the question; here is the edition's answer — a technique for interrogating a repository with three questions before you trust or run anything in it. First: where does execution actually start? Second: what does the project claim about itself, in its own docs? Third: where is the mass — the biggest files, where the risk and the complexity usually live? You can answer all three without changing a single file, and the Run this block below does exactly that, read-only, against your own repository. It lists the entry points a manifest or main file reveals, surfaces the documentation, and ranks the largest files so you know where your limited attention should go.

Concretely: point it at a repository an agent just generated or modified. You get an inventory — the entry points, the stated purpose, the heavyweight files — in seconds, before any code executes. That inventory is your evidence-gathering pass. If the entry points include a script nobody mentioned, or the biggest file is something the assistant described as "a small helper," you have found the gap between the story and the code. That gap is exactly where generated code goes wrong, and it is invisible from the outside of a chat window. The script stops before editing anything on purpose: evidence collection and modification are different jobs, and mixing them is how reviews become rubber stamps.

What to do with what you find

Treat the inventory as a reading order, not a verdict. Start with the entry points, because that is what will actually run. Skim the docs to see what the project promises, then check the biggest files against those promises. If the docs and the code disagree, believe the code — and update your mental model, or send the agent back with a specific, file-level instruction. Specific beats general: "explain what this function does before I run it" produces evidence; "make it better" produces more code.

Your next step is small: run the inspection on the last repository an agent touched for you, today, and compare the output to what you remember being told. If the two match, you have earned a little confidence. If they don't, you have just caught something a green checkmark would have waved through — and that is the whole job of review, whether a human or a very confident autocomplete wrote the lines.

Why it matters

  • AI-generated code arrives faster than you can read it, so your targeted reading is now the main quality gate.
  • A read-only inventory of entry points, docs, and biggest files turns vague review anxiety into a concrete reading order.
  • Green builds and confident assistant messages are outputs, not evidence — the gap between them and the code is where bugs hide.

#!/usr/bin/env python3
"""Read-only audit of editor harness settings.

Scans the default settings paths for VS Code, Insiders, Cursor, and VSCodium.
Prints only keys whose names contain "harness" or "sessiontarget". It never
prints the whole settings file and never writes anything.
"""
import os
import pathlib
import platform
import re
import sys

HOME = pathlib.Path.home()
EDITORS = ["Code", "Code - Insiders", "Cursor", "VSCodium"]
PATTERN = re.compile(
    r'"([^"]*(?:harness|sessiontarget)[^"]*)"\s*:\s*'
    r'("(?:[^"\\]|\\.)*"|true|false|null)',
    re.IGNORECASE,
)


def settings_paths():
    paths = []
    for name in EDITORS:
        if os.name == "nt":
            appdata = pathlib.Path(os.environ.get("APPDATA", HOME / "AppData/Roaming"))
            paths.append(appdata / name / "User" / "settings.json")
        elif platform.system() == "Darwin":
            paths.append(
                HOME / "Library/Application Support" / name / "User" / "settings.json"
            )
        else:
            paths.append(HOME / ".config" / name / "User" / "settings.json")
    return paths


def main():
    scanned = 0
    with_keys = 0
    for path in settings_paths():
        if not path.is_file():
            continue
        scanned += 1
        try:
            text = path.read_text(encoding="utf-8", errors="replace")
        except OSError as exc:
            print(f"{path}: cannot read ({type(exc).__name__})")
            continue
        matches = PATTERN.findall(text)
        print(path)
        if not matches:
            print("  no harness-related keys")
            continue
        with_keys += 1
        for key, value in matches:
            print(f"  {key} = {value}")

    if not scanned:
        print("No editor settings files found.")
        return 1

    print(f"\nScanned {scanned} settings file(s); {with_keys} had harness-related keys.")
    return 0


if __name__ == "__main__":
    sys.exit(main())
